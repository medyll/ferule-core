## 15. Agent Startup Heuristic

### Purpose

`llms.txt`, `README.md`, and `USER-NOTES.md` are the primary anchors for agent orientation. Any agent or skill operating on an application MUST execute the startup sequence before any write action.

### 15.1 `llms.txt` — Machine-Readable Index

Every project MUST include an `llms.txt` at its root. Structure:

```markdown
# <Project Name>

> Brief description.

## Documentation

- [README](./README.md) — Project overview and status
- [Phase 1](./phase-1-repair.md) — Phase description
- [Bug Reports](./reports/bug-reports.md) — Known bugs
- [User Notes](./USER-NOTES.md) — User instructions
```

### 15.2 Startup Sequence

Before any write action:

1. **Read `llms.txt`** — Identify project type, structure, available documents
2. **Read `README.md`** — Gather overview, status, file map
3. **Read `USER-NOTES.md`** — Apply instructions. If non-conformant, normalize per §10
4. **If not yet scaffolded** — Check for `BLUEPRINT.md` → normalize to USER-NOTES.md, then scaffold. If only `SCRATCHPAD.md` exists → DO NOT auto-normalize. Wait for human instruction.
5. **Read phase files** — Navigate via links from `README.md`

### 15.2.1 SCRATCHPAD Detection

If an agent detects `SCRATCHPAD.md` at the application root:

| Condition | Action |
|-----------|--------|
| SCRATCHPAD exists, no BLUEPRINT | **Do NOT normalize.** The file is raw capture — it belongs to the user. The agent may tidy it if asked, but must never auto-convert it. |
| BLUEPRINT exists | Normalize to USER-NOTES.md, then scaffold per §10 |

**Rationale:** SCRATCHPAD is a freeform capture file. Auto-normalization would corrupt the user's raw thinking process. Only the human decides when raw notes are ready for rationalization.

**Scope:** Applies to agents AND skills. A skill that bypasses this sequence before any write action is non-compliant.

### 15.3 Documentation Ingestion Priority

| File | Audience | Purpose | Priority |
|------|----------|---------|----------|
| **llms.txt** | AI Agents | High-speed indexing | Critical |
| **README.md** | Human/AI | Overview, entry-point | High |
| **USER-NOTES.md** | AI Agents | User instructions | High |
| **Phase files** | Human/AI | Task details | Medium |
| **Bug reports** | Human/AI | Known issues | Medium |
| **Deployment report** | Human/AI | Final state | Low |

### 15.4 Token Efficiency Rules

| Rule | Detail |
|------|--------|
| **Standardized headers** | Use `README.md`, `Structure`, `Summary Table`, `Current System State` |
| **Fenced code blocks** | Always include language identifiers |
| **Link integrity** | Use relative paths for autonomous navigation |
| **No paragraphs > 2 sentences** | Keep it scannable |
| **Tables over prose** | Structured data is easier for agents to parse |

## 16. Maintenance & Debugging Standards

### Purpose

Every application MUST expose a standardized maintenance interface for `core-squad` to monitor, diagnose, and repair without application-specific tools.

### Learned Rules

Operational rules derived from real incidents are stored in:
`core-standard/development/rules/`

These files are auto-populated by the learning cycle — do not edit manually. Agents MUST read relevant rule files before any maintenance or repair intervention.

| File | Content |
|------|---------|
| [maintenance-rules.md](../core-standard/development/rules/maintenance-rules.md) | Source of truth, safety nets, restart protocol, deadlock prevention, log hygiene, repair scope, crisis detection, distributed responsibility, panic room protocol |

### 16.1 Maintenance Dashboard Interface

Required in `README.md` or `maintenance.md`:

```markdown
## ⚙️ Maintenance & Debugging

| Component | Status | Last Check | Metrics |
|-----------|--------|------------|---------|
| **Core Process** | ✅ Active | 2026-04-10 16:00 | PID: 12345 |
```

### Rules

| Rule | Detail |
|------|--------|
| **Location** | `core-ferule/<app-name>/README.md` under `## Maintenance & Debugging` |
| **Read-Only** | LLMs MUST read, MUST NOT write — only scripts or `core-squad` may update |
| **Global Aggregation** | `core-squad` aggregates all dashboards into `status-dashboard.md` |
| **`status-dashboard.md` generation** | MUST be generated by `core-squad` or a dedicated script — LLMs MUST NOT write it directly. It is a generated output, not a source of truth. The generator MUST read raw sources (logs, JSONL, system files) — never other status files. |

---

### 16.2 Generic Scanner Compliance

Allowed formats: Markdown tables, valid YAML/JSON, line-based logs with timestamps. Prohibited: binary formats, unstructured dumps, state hidden in comments.

---

### 16.3 Post-Restart Validation Protocol

After any restart, MUST run:

1. **Process Check** — verify PID
2. **Health Check** — `node core-squad/scripts/maintenance-scanner.mjs --target <app> --type <queue|yaml|json>` → must return `health: "healthy"`
3. **Log Verification** — last 10 lines, check for `ERROR` or `FATAL`

### Rules

| Rule | Detail |
|------|--------|
| **Mandatory** | After every `openclaw gateway --force` or watcher restart |
| **Failure** | Step 2 fails → Escalation Level 2 |
| **Reporting** | Results → `core-squad/ocm-STATUS-REPORT.md` |

## 17. Crisis Investigation Protocol — Midnight Hell

### Purpose

A **midnight-hell** is a structured investigation for systemic failures where normal bug reporting is insufficient. Produces an audit trail, causal analysis, and conclusions that feed back into `core-standard`.

### Structure

```
reports/midnight-hell/<YYYY-MM-DD>/
├── midnight-steps.md       ← Entry point
├── 01-grouping.md
├── 02-timeline.md
├── 03-matrix.md
├── 04-conclusions.md       ← REQUIRED
└── <NN>-<slug>.md
```

### Lifecycle

```
1. OPEN    → Create reports/midnight-hell/<YYYY-MM-DD>/ + midnight-steps.md
2. ANALYZE → grouping → timeline → matrix → conclusions
3. CLOSE   → 04-conclusions.md MUST be completed
4. PULL    → Extract TD proposals → core-standard
```

### 04-conclusions.md Required Sections

- **Root Causes** — problem, impact, fix per cause
- **Contributing Factors** — lessons
- **Preventive Actions** — priority table
- **Responsibility Map** — actors, index (0–100%), synthesis (distributed, never singular blame)
- **Evidence Index** — conclusion ↔ evidence files

### midnight-steps.md Structure

```markdown
# Midnight Hell — Analysis Steps

**Date:** YYYY-MM-DD
**Subject:** One sentence — what failed.
**Source files:** N files across M zones
**Analyst:** <Agent name>

## Control Table

| Step | Phase | Status | Started | Completed | Output file |
|------|-------|--------|---------|-----------|-------------|
```

### status-dashboard.md Rules

| Rule | Detail |
|------|--------|
| **Generated, never written** | MUST be generated by script — never hand-written by an LLM |
| **Read-only for LLMs** | LLMs read raw sources (logs, JSONL) — never `status-dashboard.md` |
| **Generator** | `core-squad` or dedicated script |

> **Why:** LLM-written status files become circular references — root cause of the 13h silence (09-04-2026 midnight-hell).

### Rules

| Rule | Detail |
|------|--------|
| **Date folder** | Each crisis in its own `<YYYY-MM-DD>/` folder |
| **Entry point** | `midnight-steps.md` always first |
| **Read-only sources** | Never modify source files during analysis |
| **Conclusions required** | `04-conclusions.md` MUST be completed |
| **Pull obligation** | Every closed midnight-hell MUST produce ≥1 TD proposal to `core-standard` |
